# 1.1 — Include the visitor's details in contact emails

**Status:** Agreed
**Branch:** `fix/1.1-reply-to`
**Plan reference:** RMT_Website_Plan.docx, task 1.1

## Goal

When a visitor sends the contact form, the therapist can see who wrote and can press **Reply** in
their inbox to answer the visitor directly. A missing `Mailgun:ToEmail` setting fails loudly instead
of sending an empty request.

## Current state

- `Services/EmailSenderService.cs:17`: `SendEmailAsync(email, subject, htmlMessage)` receives the
  visitor's address in `email` but never uses it. The therapist gets the subject and message only.
- `EmailSenderService.cs:35`: the form content is only built `if (toEmail != null)`. With no
  `ToEmail`, the request goes to Mailgun with **no body**, and the error only shows up as a Mailgun
  failure response.
- `EmailSenderService.cs:26`: the missing-config branch creates a logger and never uses it. Proper
  logging is task 1.6, not this one.
- `Components/Pages/ContactUs.razor:62` already catches exceptions and logs them with `ILogger`, so
  throwing a clear `InvalidOperationException` is enough to get a clear logged error.
- Tests (`EmailSenderServiceTests.cs`, on `master`): `SendEmailAsync_ValidConfig_SendsRecipientSubjectAndMessage`
  asserts the text is passed through **unchanged**. Step 4 below changes that on purpose, so this
  test's `text` assertion gets updated with the new expected value.

## Approach

Test-first (CLAUDE.md: every bug fix includes a test that fails before the fix). For each behaviour:
write the test, run it and **watch it fail**, make the smallest code change that passes it, rerun.

1. **Reply-To:** add the Mailgun form field `h:Reply-To` = visitor's email. Mailgun turns any
   `h:<Name>` field into an email header, so this sets the real `Reply-To` header.
2. **Body header:** start the `text` field with `From: {email}`, a blank line, then the message, so
   the address is visible even if a mail client ignores Reply-To.
3. **Missing ToEmail:** include `ToEmail` in the existing missing-config check and throw
   `InvalidOperationException`, like `ApiKey` and `BaseUrl`.

Considered and rejected: sending **from** the visitor's address. Mailgun would be sending as a domain
it doesn't own, so SPF/DMARC checks would fail and the email would land in spam. That's why the
standard approach is our own `from` plus the visitor in `Reply-To`.

Also dropped: the Word plan's subject prefix (`[Website inquiry] {subject}`). The subject stays
exactly as the visitor typed it (see Decisions).

## Steps

1. Create `fix/1.1-reply-to` from an up-to-date `master`.
2. Missing ToEmail: add `[InlineData("Mailgun:ToEmail")]` to
   `SendEmailAsync_MissingRequiredSetting_ThrowsWithoutSending`. Run it: **red** (a request is sent).
   Add `toEmail == null` to the config check and remove the `if (toEmail != null)` wrapper. **Green.**
3. Reply-To: new test `SendEmailAsync_ValidConfig_SetsReplyToVisitorEmail` asserting
   `form["h:Reply-To"]` is the visitor's address. **Red**, then add the field. **Green.**
4. Body header: new test `SendEmailAsync_ValidConfig_MessageStartsWithVisitorEmail`. **Red**, then
   build the text as `From: {email}` + blank line + message. **Green.** Update the `text` assertion in
   `..._SendsRecipientSubjectAndMessage`.
5. Validate the visitor's email in the service: new test
   `SendEmailAsync_InvalidVisitorEmail_ThrowsWithoutSending` (a `[Theory]` with bad addresses,
   including one containing a line break). **Red**, then check it with `MailAddress.TryCreate` and throw
   `ArgumentException` before building the request. **Green.**
6. Manual check: run the site, send a test inquiry through `/contact`, and confirm in the inbox that
   the body shows the visitor's address, and **Reply** addresses the visitor.
   Uses the real Mailgun key from user secrets, so the developer does this step.

## Decisions (agreed 2026-09-25)

- **Who types:** the developer writes the tests and the fixes, one red/green cycle at a time; the
  assistant reviews each cycle.
- **Service validates `email`:** yes (step 5). The address goes straight into an email header, and
  the service can't assume every caller validated it first (defence in depth).
- **No subject prefix:** the subject arrives exactly as the visitor typed it. Differs from the Word
  plan's step 3 on purpose.
