### Hero: key concepts

- **`<img>` behind the text, not a CSS `background-image`.** The hero photo is the largest thing on
  the first screen, so it's what Google measures as *Largest Contentful Paint* (LCP). An `<img>` in
  the HTML is found immediately by the browser's preload scanner. A CSS background is only found
  after the CSS loads. So: `<img ... fetchpriority="high" width height alt="">`, positioned behind the text with
  `object-fit: cover`. `alt=""` is right here, because the photo is decorative and the headline says what matters.
- **Overlay strong enough for any photo.** White text has to pass 4.5:1 even over the brightest
  part of the image. With a black overlay at 55% opacity, a pure-white pixel becomes about `#737373`,
  and white on that is **4.74:1**. So 0.55 just passes, and the plan uses 0.6 (5.7:1) for margin. It's a
  token, `--hero-overlay`, in `app.css`, not a hard-coded colour.
- **Responsive height:** `min-height: 60vh` (70vh on desktop) instead of 600px. `min-height`
  lets the box grow if the text needs more room (a long headline at 320px, or 200% zoom).
- Buttons: **Book an appointment** is the primary button (cyan, like Book now) and goes to `/contact` for now.
  **View services** is secondary (white outline) and goes to `/services`. Both are 44px+ tall.

### One source of truth for services and prices

The Home preview and the Services page must never show different prices. So the data moves out of
the markup into a small model and service, following clean architecture: the page asks for data
and doesn't own it.

```
Models/ServiceOffering.cs       record: Name, Description, Durations (minutes + price)
Services/IServiceCatalog.cs     GetAll(); one place that knows what the clinic offers
Services/ServiceCatalog.cs      in-memory list (today's five Swedish prices); 4.3 can later read it from config
```

- `Services.razor` renders its existing table from `IServiceCatalog`. It looks the same, but the
  data is no longer hard-coded there. 2.5 redesigns that page later.
- The Home preview shows each offering with "from $X", computed as the lowest price, so it can't
  go stale.
- Today there's one offering (Swedish massage, 30–90 min, from $90), so the "preview" is a single card plus
  the link. More cards appear automatically when more treatments are added (Q5).

### Architecture: one source of truth for prices

```
Models/ServiceOffering.cs        record ServiceOffering(string Name, IReadOnlyList<ServiceOption> Options)
                                 record ServiceOption(int Minutes, decimal Price)
                                 + StartingPrice (lowest Price), MinMinutes / MaxMinutes
Services/IServiceCatalog.cs      IReadOnlyList<ServiceOffering> GetAll()
Services/ServiceCatalog.cs       today's five Swedish prices, in memory
Program.cs                       builder.Services.AddSingleton<IServiceCatalog, ServiceCatalog>();
```

- **`Services.razor`** renders its existing table from `IServiceCatalog`, with the same rows and the same
  "30 minute Massage" / "$90.00" text, so the page looks identical. (Its redesign is 2.5.)
- **Home** injects the same catalog. "from $90.00" is *calculated*, so a price change in one place updates both pages.
- **Key concept: culture-safe money formatting.** `90m.ToString("C")` uses the *server's* culture: it
  shows "$90.00" on a Canadian machine but "90,00 €" on a French one, and a cloud host's culture is
  often unpredictable. Prices are formatted with `CultureInfo("en-CA")` explicitly, in one place
  (`ServiceOption.FormattedPrice`), so every page and test agrees.
- Why an interface: pages depend on `IServiceCatalog`, not on where the data lives. 4.3 ("make content
  editable without code changes") can later swap in a config- or file-backed catalog with no page changes.
  It's the same dependency-injection pattern as `IEmailSender`, so no ADR is needed.
