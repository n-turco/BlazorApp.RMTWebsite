# 6.2 — Automated testing strategy and test suite

**Status:** In progress (PR 1)
**Branch:** `chore/6.2-test-project` (first PR), then `chore/6.2-integration-tests`, `chore/6.2-e2e-tests`
**Plan reference:** RMT_Website_Plan.docx, task 6.2

## Goal

Put a safety net in place before new features: a test project that runs with `dotnet test`,
covers the email service, the contact form model, and every page, and never needs real
Mailgun credentials. From then on, every fix and feature ships with tests in the same PR.

## Current state

- No test project. `BlazorApp.RMTWebsite.slnx` contains only the web project.
- `Services/EmailSenderService.cs` takes `HttpClient` and `IConfiguration` through its
  constructor, which is good: tests can pass a fake `HttpClient` and in-memory config
  without touching Mailgun.
  - It never sends the visitor's email address (`email` parameter is unused), which is bug 1.1.
  - If `Mailgun:ToEmail` is missing it still sends a request with no body instead of failing.
  - It writes to `Console` and creates a throwaway logger (task 1.6).
- `Models/EmailInquiry.cs` uses DataAnnotations (`Required`, `EmailAddress`, `StringLength` 30/1000),
  which can be tested directly with `Validator.TryValidateObject`.
- `Program.cs` is a public `Program` class, so `WebApplicationFactory<Program>` can start the whole
  site in memory for integration tests.
- Pages use `<h3>` instead of `<h1>` (fixed by 1.4 / 3.3). **Tests must describe how the site works
  today**, so the "exactly one `<h1>`" check waits until those tasks, when it will be added alongside the fix.
- `ContactUs.razor` uses `[SupplyParameterFromForm]` with an initializer (BL0008) and static SSR.
  bUnit's support for SSR form posting is limited, so form *submission* is better tested through
  integration tests (real HTTP POST) than bUnit.

## Approach

**The testing pyramid:** many fast unit tests, fewer integration/component tests, and a few slow
end-to-end tests.

| Layer | Tool | What it covers |
|---|---|---|
| Unit | xUnit | `EmailInquiry` validation, `EmailSenderService` request building and error handling |
| Integration | `Microsoft.AspNetCore.Mvc.Testing` (`WebApplicationFactory`) | Every route returns 200 with the right `<title>`, unknown routes show Not Found, contact form POST with a fake `IEmailSender` |
| Component | bUnit | Rendering of components with logic (contact form validation messages, footer links) |
| End-to-end | Playwright | Real browser at 375px and desktop: pages load, contact form round trip |
| Coverage | coverlet | Report per run; aim for about 80% on `Services` and `Models` |

Alternatives considered: NUnit/MSTest (all fine; xUnit is the most common in ASP.NET Core docs and
samples), Moq for fakes (a tiny hand-written `HttpMessageHandler` is clearer to learn from and needs
no extra package), and Selenium (Playwright is faster and has first-class .NET support).

**Split into three small PRs** so each one can be understood and reviewed on its own:

1. **Test project and unit tests.** The foundation.
2. **Integration and component tests.** Tests the whole app in memory.
3. **End-to-end tests and coverage.** Best done with, or after, CI (6.3), because browsers need installing.

## Steps

### PR 1 — `chore/6.2-test-project`
1. `dotnet new xunit -o BlazorApp.RMTWebsite.Tests`, add it to the `.slnx`, reference the web project.
2. Add a `FakeHttpMessageHandler` test helper that records the request and returns a canned response.
3. `EmailInquiryTests`: valid model passes; each missing field fails; bad email fails; subject > 30
   and message > 1000 characters fail; boundary values (exactly 30 / 1000) pass.
4. `EmailSenderServiceTests`: posts to `Mailgun:BaseUrl`; Basic auth header is `api:<key>` in Base64;
   form contains `to`, `subject`, `text`; throws when config is missing; throws on a non-success response.
5. Write ADR `docs/decisions/0002-testing-stack.md`.
6. Update `CLAUDE.md` (commands and a "Testing" convention) and add a data-flow diagram in
   `Visual_dataflow_features/` showing how a unit test swaps Mailgun for the fake handler.

### PR 2 — `chore/6.2-integration-tests`
7. Add `Microsoft.AspNetCore.Mvc.Testing`, and a `SiteFactory` that swaps `IEmailSender` for a fake that
   records calls.
8. Theory test over every route (`/`, `/services`, `/about`, `/contact`, `/faq`): 200 + expected `<title>`.
9. Unknown route returns the Not Found page.
10. Contact form: GET the page, read the antiforgery token, POST a valid form, and check the fake sender was
    called once and the success message shows. An invalid POST shows validation messages and sends nothing.
11. Add bUnit and component tests where they add value (e.g. `SiteFooter` only renders social links with URLs).

### PR 3 — `chore/6.2-e2e-tests`
12. Add a Playwright test project that starts the site and checks each page at 375px and 1280px.
13. Add coverlet coverage collection and document the command.

## Notes from implementation

- The `xunit3` template targeted .NET 8; changed to `net10.0` to match the app.
- xUnit v3 on the .NET 10 SDK only runs through Microsoft.Testing.Platform, so the template's
  `global.json` (`"test": { "runner": "Microsoft.Testing.Platform" }`) is required. The classic
  VSTest packages (`Microsoft.NET.Test.Sdk`, `xunit.runner.visualstudio`) are not needed.
- Checked that the tests catch real mistakes: changing the auth prefix from `api:` to `user:` made
  `SendEmailAsync_ValidConfig_UsesBasicAuthWithApiKey` fail, then it was reverted.
