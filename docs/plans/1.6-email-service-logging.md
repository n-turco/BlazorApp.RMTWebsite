# 1.6 — Use proper logging in the email service

**Status:** Agreed
**Branch:** `fix/1.6-email-service-logging`
**Plan reference:** RMT_Website_Plan.docx, task 1.6

## Goal

When a contact email fails to send, the site owner can see a clear entry in the host's log stream
saying what went wrong (the Mailgun status code), without the visitor's message or Mailgun's full
response ending up in the logs. Nothing changes for the visitor.

## Current state

- `BlazorApp.RMTWebsite/Services/EmailSenderService.cs:58` and `:62` write to `Console.WriteLine`,
  including the full Mailgun response body. Console output is not structured, has no log level,
  and is easy to lose on a production host.
- `EmailSenderService.cs:26` builds a brand-new `LoggerFactory` and logger inside the missing-config
  branch and then never uses it. It is dead code, and creating a factory by hand bypasses the
  logging the host already configured.
- `EmailSenderService.cs:59` puts the full response body in the exception message.
  `Components/Pages/ContactUs.razor:68` logs that exception, so the response body reaches the logs
  by a second route even once `Console.WriteLine` is gone.
- `ContactUs.razor` already injects `ILogger<ContactUs>` correctly, so the pattern exists in the app.
- The tests build the service in one place, `CreateService` in
  `BlazorApp.RMTWebsite.Tests/Services/EmailSenderServiceTests.cs:44`, so adding a constructor
  parameter only needs one test-side change.

## Approach

Inject `ILogger<EmailSenderService>` through the existing primary constructor. ASP.NET Core registers
`ILogger<T>` automatically, so `Program.cs` needs no change: the typed `HttpClient` registration
resolves the extra constructor parameter from dependency injection (DI).

Log with **message templates**, not string interpolation:

```csharp
// Good: StatusCode is stored as a named, searchable property
_logger.LogError("Mailgun rejected the contact email with status {StatusCode}.", (int)response.StatusCode);

// Avoid: the value is baked into the text and the analyzer warns (CA2254)
_logger.LogError($"Mailgun rejected the contact email with status {response.StatusCode}.");
```

What gets logged:

| Situation | Level | Logged | Not logged |
|---|---|---|---|
| Required config missing | Error | Which *key names* are missing | The key values |
| Invalid visitor address | Warning | That the address was rejected | The address itself |
| Mailgun returns non-success | Error | Numeric status code | Response body, visitor message |
| Sent successfully | Information | That a contact email was sent | Address, subject, message |

The exception thrown on a failed send changes to carry the status code only, so the response body
no longer leaks through the `ContactUs` log entry.

**Testing the logs.** Add a small hand-written `FakeLogger<T>` in `Tests/Fakes/` that records each
entry's level and text. This matches the existing `FakeHttpMessageHandler` and ADR 0002 (hand-written
fakes, no mocking library).

Alternatives considered:

- *`Microsoft.Extensions.Diagnostics.Testing` package (ships a ready-made `FakeLogger<T>`).* Less
  code, but a new dependency for about 25 lines, and writing the fake shows how `ILogger` works.
- *`NullLogger<T>` in tests.* Simplest, but then nothing proves the right things are logged or that
  personal details are left out.
- *Rename `IEmailSender` to our own `IContactEmailService` now.* The plan says "consider". It touches
  `Program.cs`, `ContactUs.razor`, `_Imports.razor` and the tests, and is a design choice that
  deserves an ADR, so it is left for a separate PR (see open questions).

## Steps

1. Create branch `fix/1.6-email-service-logging` from `master`.
2. Add `Tests/Fakes/FakeLogger.cs`: implements `ILogger<T>`, stores `(LogLevel, message)` entries.
3. Update `CreateService` in the tests to pass a `FakeLogger<EmailSenderService>` and return or
   expose it so tests can inspect it.
4. Write the new tests first and watch them fail (red):
   - `SendEmailAsync_MailgunReturnsError_LogsErrorWithStatusCode`
   - `SendEmailAsync_MailgunReturnsError_DoesNotLogResponseBody`
   - `SendEmailAsync_MailgunReturnsError_ExceptionOmitsResponseBody`
   - `SendEmailAsync_ValidConfig_LogsInformationWithoutVisitorDetails`
   - `SendEmailAsync_MissingRequiredSetting_LogsError`
5. Add `ILogger<EmailSenderService> logger` to the primary constructor.
6. Delete the unused `LoggerFactory.Create(...)` line and log the missing key names instead.
7. Replace both `Console.WriteLine` calls with `LogError` / `LogInformation` using templates.
8. Change the failure exception message to the status code only; stop reading the response body
   if nothing else needs it.
9. Tidy the stale comments at the top of `SendEmailAsync` ("move to proper logging later").
10. Run the tests (green), `dotnet build`, and `dotnet format --verify-no-changes`.
11. Add `Visual_dataflow_features/1.6-email-service-logging.md` with a flow chart of what is logged
    at each exit of `SendEmailAsync`.
12. Run the site, break the config on purpose (e.g. a wrong `Mailgun:BaseUrl` in user secrets or an
    environment variable), submit the form, and confirm the error shows in the terminal log.
